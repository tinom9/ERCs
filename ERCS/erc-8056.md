## Abstract

This EIP proposes a standard extension to [ERC-20](./eip-20.md) tokens that enables issuers to apply an updatable multiplier to the underlying amount of tokens. This allows for efficient representation of scaled token amounts without requiring actual token minting, transfers, or rebases. The extension provides a cosmetic layer that modifies how token balances are displayed to users while maintaining the underlying token economics.

## Motivation

Current ERC-20 implementations lack an efficient mechanism to handle real-world asset scenarios:

- **Stock splits**: When a company performs a 2-for-1 stock split, all shareholders should see their holdings double. Currently, this requires minting new tokens to all holders, which is gas-intensive and operationally complex. Moreover, the internal accounting in DeFi protocols would break from such a split.

- **Wrapped rebasing tokens**: May represent underlying rebasing tokens, accrual of rewards, or compounded interest.

- **Management fees**: Fund tokens may accrue fees that reduce the net asset value per share over time. A decreasing multiplier can reflect this without burning tokens from holders.

The inability to efficiently handle these scenarios limits the adoption of tokenized real-world assets (RWAs) on Ethereum. This EIP addresses these limitations by introducing a multiplier mechanism that adjusts the displayed balance without altering the actual token supply.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

### Interface

```solidity
interface IScaledAmount {
    /**
     * @notice Emitted when the scaled multiplier is updated.
     * @param oldMultiplier Old scaled multiplier
     * @param newMultiplier New scaled multiplier
     * @param effectiveAtTimestamp Timestamp at which the new multiplier becomes effective
     */
    event ScaledMultiplierUpdated(uint256 oldMultiplier, uint256 newMultiplier, uint256 effectiveAtTimestamp);

    /**
     * @notice Emitted when a token transfer is made.
     * @dev Optional event, it may not be emitted in transfers.
     * @param from Address of the sender
     * @param to Address of the recipient
     * @param amount Amount of tokens transferred in raw units
     * @param scaledAmount Amount of tokens transferred in scaled units
     */
    event TransferWithScaledAmount(address indexed from, address indexed to, uint256 amount, uint256 scaledAmount);

    /**
     * @notice Returns the current unit multiplier, represented with 18 decimals (1e18 = 1.0).
     * @return multiplier Current unit multiplier
     */
    function unitMultiplier() external view returns (uint256 multiplier);
}

interface IScaledAmountBalanceAndSupply {
    /**
     * @notice Returns the scaled balance of an account.
     * @param account Address of the account
     * @return scaledBalance Scaled balance
     */
    function balanceOfScaled(address account) external view returns (uint256 scaledBalance);

    /**
     * @notice Returns the scaled total supply of the token.
     * @return scaledTotalSupply Scaled total supply
     */
    function totalSupplyScaled() external view returns (uint256 scaledTotalSupply);
}

interface IScaledAmountConversion {
    /**
     * @notice Converts a raw token amount to its scaled representation.
     * @param rawAmount Raw token amount
     * @return scaledAmount Scaled token amount
     */
    function toScaledAmount(uint256 rawAmount) external view returns (uint256 scaledAmount);

    /**
     * @notice Converts a scaled token amount to its raw representation.
     * @param scaledAmount Scaled token amount
     * @return rawAmount Raw token amount
     */
    function fromScaledAmount(uint256 scaledAmount) external view returns (uint256 rawAmount);
}
```

### ERC-165 Interface Identifiers

Contracts implementing this standard MUST implement the [ERC-165](./eip-165.md) `supportsInterface` function and return `true` for the following interface identifiers:

| Interface                        | Identifier   | Required |
| -------------------------------- | ------------ | -------- |
| `IScaledAmount`                  | `0x60dadf33` | Yes      |
| `IScaledAmountBalanceAndSupply`  | `0x4b22410b` | No       |
| `IScaledAmountConversion`        | `0xc7821c7a` | No       |

The interface identifiers are calculated as the XOR of all function selectors in the interface, excluding events.

### Implementation Requirements

1. Multiplier Precision: The unit multiplier MUST use 18 decimal places for precision (1e18 represents a multiplier of 1.0).

2. Backwards Compatibility: The standard ERC-20 functions (balanceOf, transfer, transferFrom, etc.) MUST continue to work with raw amounts.

3. Event Emission: The `ScaledMultiplierUpdated` event MUST be emitted whenever the multiplier is changed. The `TransferWithScaledAmount` event CAN be emitted whenever a token transfer is made.

4. Zero Multiplier Prevention: The `unitMultiplier()` function MUST NOT return zero to prevent division by zero errors in conversion functions.

### Reference Implementation

```solidity
contract ScaledToken is ERC20, ERC165, IScaledAmount, IScaledAmountBalanceAndSupply, IScaledAmountConversion, Ownable {
    uint256 private constant MULTIPLIER_DECIMALS = 1e18;
    uint256 private _unitMultiplier = MULTIPLIER_DECIMALS; // Initially 1.0
    uint256 public nextUnitMultiplier = MULTIPLIER_DECIMALS;
    uint256 public nextUnitMultiplierEffectiveAt = 0;

    constructor(string memory name, string memory symbol) ERC20(name, symbol) Ownable(msg.sender) {}

    function supportsInterface(bytes4 interfaceId) public view virtual override returns (bool) {
        return
            interfaceId == type(IScaledAmount).interfaceId ||
            interfaceId == type(IScaledAmountBalanceAndSupply).interfaceId ||
            interfaceId == type(IScaledAmountConversion).interfaceId ||
            super.supportsInterface(interfaceId);
    }

    function unitMultiplier() public view override returns (uint256) {
        if (block.timestamp >= nextUnitMultiplierEffectiveAt) {
            return nextUnitMultiplier;
        } else {
            return _unitMultiplier;
        }
    }

    function toScaledAmount(uint256 rawAmount) public view override returns (uint256 scaledAmount) {
        return (rawAmount * unitMultiplier()) / MULTIPLIER_DECIMALS;
    }

    function fromScaledAmount(uint256 scaledAmount) public view override returns (uint256 rawAmount) {
        return (scaledAmount * MULTIPLIER_DECIMALS) / unitMultiplier();
    }

    function balanceOfScaled(address account) public view override returns (uint256 scaledBalance) {
        return toScaledAmount(balanceOf(account));
    }

    function totalSupplyScaled() public view override returns (uint256 scaledTotalSupply) {
        return toScaledAmount(totalSupply());
    }

    function setScaledMultiplier(uint256 newMultiplier, uint256 effectiveAtTimestamp) external onlyOwner {
        require(newMultiplier > 0, "Multiplier must be positive");

        uint256 oldMultiplier = unitMultiplier();
        if (block.timestamp >= nextUnitMultiplierEffectiveAt) {
            _unitMultiplier = nextUnitMultiplier;
        }
        nextUnitMultiplier = newMultiplier;
        nextUnitMultiplierEffectiveAt = effectiveAtTimestamp;

        emit ScaledMultiplierUpdated(oldMultiplier, newMultiplier, effectiveAtTimestamp);
    }

    function _update(address from, address to, uint256 amount) internal virtual override {
        super._update(from, to, amount);
        uint256 scaledAmount = toScaledAmount(amount);
        emit TransferWithScaledAmount(from, to, amount, scaledAmount);
    }
}
```

## Rationale

Design Decisions:

1. Separate Scaled Functions: Rather than modifying the core ERC-20 functions, we provide separate scaled-specific functions. This ensures backward compatibility and allows integrators to opt-in to the scaling feature.

2. 18 Decimal Precision: Using 18 decimals for the multiplier provides sufficient precision for most use cases while aligning with Ethereum's standard decimal representation.

3. Raw Amount Preservation: All actual token operations continue to use raw amounts, ensuring that the multiplier is purely a display feature and doesn't affect the underlying token economics.

Alternative Approaches Considered:

1. Rebasing Tokens: While rebasing tokens adjust supply automatically, they create complexity for integrators and can break composability with DeFi protocols.

2. Wrapper Tokens: Creating wrapper tokens for each adjustment event adds unnecessary complexity and gas costs.

3. Index/Exchange Rate Tokens confer similar advantages to the proposed Scaled Amount approach, but are ultimately less intuitive and require more calculations on the UI layers.

4. Off-chain Solutions: Purely off-chain solutions lack standardization and require trust in centralized providers.

### Backwards Compatibility

This EIP is fully backwards compatible with ERC-20. Existing ERC-20 functions continue to work as expected, and the scaling features are opt-in through additional functions.

### Test Cases

Example test scenarios:

1. Initial Multiplier Test:
   - Verify that initial multiplier is 1.0 (1e18)
   - Confirm `balanceOf` equals `balanceOfScaled` initially

1. Stock Split Test (Forward):
   - Set multiplier to 2.0 (2e18) for 2-for-1 split
   - Verify scaled balance is double the raw balance
   - Confirm conversion functions work correctly

1. ERC-165 Support Test:
   - Verify `supportsInterface` returns `true` for `IScaledAmount` interface ID
   - Verify `supportsInterface` returns `true` for optional interfaces if implemented

## Security Considerations

1. Multiplier Manipulation
   - Unauthorized changes to the unit multiplier could mislead users about their holdings
   - Implementations MUST use robust access control mechanisms
   - The `setScaledMultiplier` function MUST be restricted to authorized addresses (e.g., contract owner or a designated role)

1. Integer Overflow
   - Risk of overflow when applying the multiplier
   - Use SafeMath or Solidity 0.8.0+ automatic overflow protection
   - Implementations MUST handle potential overflow when applying the multiplier

1. User Confusion
   - Clear communication is essential when scaled amounts differ from raw amounts in the UI
   - Integrators MUST clearly indicate when displaying scaled amounts

1. Oracle Dependency
   - For automated multiplier updates, the system may depend on oracles
   - Oracle failures or manipulations could affect displayed balances

1. Rounding and Precision Loss
   - Conversion functions use integer division which rounds down
   - Round-trip conversions (`fromScaledAmount(toScaledAmount(x))`) may return a value less than the original
   - Integrators SHOULD be aware of this behavior when performing conversions

### Implementation Guide for Integrators

#### Wallet Integration

Wallets supporting this standard should:

1. Check if a token implements `IScaledAmount` interface using ERC-165

2. Display both raw and scaled amounts, clearly labeled

3. Use `balanceOfScaled()` for primary balance display

4. Handle transfers using raw amounts (standard ERC-20 functions)

**Example JavaScript integration:**

```javascript
// Interface IDs for ERC-165 detection
const ISCALED_AMOUNT_INTERFACE_ID = "0x60dadf33";
const ISCALED_AMOUNT_BALANCE_SUPPLY_INTERFACE_ID = "0x4b22410b";
const MULTIPLIER_DECIMALS = BigInt("1000000000000000000"); // 1e18

async function displayBalance(tokenAddress, userAddress) {
    const token = new ethers.Contract(tokenAddress, ScaledAmountABI, provider);
    const decimals = await token.decimals();
    const rawBalance = await token.balanceOf(userAddress);
    
    // Check if scaled amount is supported via ERC-165.
    const supportsScaled = await token.supportsInterface(ISCALED_AMOUNT_INTERFACE_ID);
    if (!supportsScaled) {
        // Standard ERC-20 token, no scaling.
        return {
            display: formatUnits(rawBalance, decimals),
            raw: formatUnits(rawBalance, decimals),
            multiplier: "1.0"
        };
    }
    
    const multiplier = await token.unitMultiplier();
    
    // Check if `balanceOfScaled` is available.
    const supportsBalanceSupply = await token.supportsInterface(ISCALED_AMOUNT_BALANCE_SUPPLY_INTERFACE_ID);
    let scaledBalance;
    if (supportsBalanceSupply) {
        scaledBalance = await token.balanceOfScaled(userAddress);
    } else {
        // Fallback: calculate manually
        scaledBalance = BigInt(rawBalance) * BigInt(multiplier) / MULTIPLIER_DECIMALS;
    }
    
    return {
        display: formatUnits(scaledBalance, decimals),
        raw: formatUnits(rawBalance, decimals),
        multiplier: formatUnits(multiplier, 18)
    };
}
```

#### Exchange Integration

Exchanges should:

1. Store and track the multiplier for each supported token

2. Display scaled amounts in user interfaces

3. Use raw amounts for all internal accounting

4. Provide clear documentation about the scaling mechanism

Example implementation:

```javascript
const ISCALED_AMOUNT_INTERFACE_ID = "0x60dadf33";
const ISCALED_AMOUNT_CONVERSION_INTERFACE_ID = "0xc7821c7a";
const MULTIPLIER_DECIMALS = BigInt("1000000000000000000"); // 1e18

class ScaledTokenHandler {
    async processDeposit(tokenAddress, amount, isScaledAmount) {
        const token = new ethers.Contract(tokenAddress, ScaledAmountABI, provider);
        
        if (!isScaledAmount) {
            // Amount is already in raw units.
            return this.recordDeposit(tokenAddress, amount);
        }
        
        // Amount is in scaled units, convert to raw.
        const supportsConversion = await token.supportsInterface(ISCALED_AMOUNT_CONVERSION_INTERFACE_ID);
        if (supportsConversion) {
            const rawAmount = await token.fromScaledAmount(amount);
            return this.recordDeposit(tokenAddress, rawAmount);
        }

        // Fallback: calculate manually using `unitMultiplier`.
        const supportsScaled = await token.supportsInterface(ISCALED_AMOUNT_INTERFACE_ID);
        if (supportsScaled) {
            const multiplier = await token.unitMultiplier();
            const rawAmount = BigInt(amount) * MULTIPLIER_DECIMALS / BigInt(multiplier);
            return this.recordDeposit(tokenAddress, rawAmount);
        }
        
        return this.recordDeposit(tokenAddress, amount);
    }
    
    async getDisplayBalance(tokenAddress, userAddress) {
        const token = new ethers.Contract(tokenAddress, ScaledAmountABI, provider);
        const rawBalance = await this.getInternalBalance(userAddress, tokenAddress);
        
        const supportsConversion = await token.supportsInterface(ISCALED_AMOUNT_CONVERSION_INTERFACE_ID);
        if (supportsConversion) {
            return await token.toScaledAmount(rawBalance);
        }
        
        // Fallback: calculate manually using `unitMultiplier`.
        const supportsScaled = await token.supportsInterface(ISCALED_AMOUNT_INTERFACE_ID);
        if (supportsScaled) {
            const multiplier = await token.unitMultiplier();
            return BigInt(rawBalance) * BigInt(multiplier) / MULTIPLIER_DECIMALS;
        }
        
        return rawBalance;
    }
}
```

#### DeFi Protocol Integration

DeFi protocols should:

1. Continue using raw amounts for all protocol operations

2. Provide helpers for displaying scaled amounts in user interfaces

3. Emit events with both raw and scaled amounts where relevant

4. Document clearly which amounts are used in calculations
